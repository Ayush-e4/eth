# x402 payments on Hedera (through MandateRegistry)

Agents pay each other per API call using x402 — the HTTP `402 Payment Required` standard.
Web2 analogy: Stripe, but the API itself quotes a price, the client pays inside the same
request, and there is no checkout page, signup or API key.

## Flow

```
Agent ──GET /plan──────────────────────────▶ Paid API (paywall middleware)
      ◀── 402 + PAYMENT-REQUIRED ───────────  0.05 USDC to 0.0.x, method transferExecutor,
                                              executors [MandateRegistry]
Agent signs PaymentAuth with its mandate
      ──GET /plan + PAYMENT-SIGNATURE ──────▶ Paid API ──/verify, /settle──▶ Our facilitator
                                                                              │ simulate, then
                                                                              │ ContractExecute
                                                                              ▼ executeTransfer
                                                                        MandateRegistry
                                                                        (rules → move USDC)
      ◀── 200 + result + PAYMENT-RESPONSE (Hedera tx id) ──
```

We use the spec's `transferExecutor` method: the payer's funds can only move through
MandateRegistry, so the **mandate's rules are enforced onchain at settlement**.

## Pieces

| Path | What |
|---|---|
| `packages/x402/src/paywall.ts` | Hono middleware: 402 when unpaid; verify → settle → run route → `PAYMENT-RESPONSE` |
| `packages/x402/src/client.ts` | `createPayingFetch`: agent-side fetch that answers 402s by signing with its mandate |
| `packages/x402/src/facilitator/validate.ts` | Spec Phase 3 steps 1–3: shape, method, executor admission (pure) |
| `packages/x402/src/facilitator/executor-facilitator.ts` | Verify (resolve, build call ourselves, simulate) and settle (`ContractExecuteTransaction`) |
| `packages/x402/src/record-checks.ts` | Spec Phase 4 proof from mirror records (parent + child) — pure, heavily tested |
| `apps/facilitator` | The facilitator service: `GET /supported`, `POST /verify`, `POST /settle`; logs to HCS |
| `apps/facilitator/scripts/demo.ts` | Live end-to-end demo |

Reused from the official SDK: `@x402/core` (v2 header encoding, payment types). The official
`@x402/hedera` facilitator only implements `cryptoTransfer`, so `transferExecutor` is ours.

## Facilitator guarantees (from the spec)

- Builds `executeTransfer(from, asset, to, amount, authorization)` from the requirements and
  `payload.payer` only — never client calldata.
- Simulates with the same gas limit it settles with; rejects on revert with the decoded reason
  (e.g. `MandateInactive`, `OverBudget`).
- Only admitted executors (MandateRegistry); rejects tokens with custom fees.
- Settlement success comes from the **record**, not the receipt: exactly `amount` from payer to
  payTo, fee payer pays only the HBAR fee, nothing else moves.
- Rejects a duplicate payload while one is in flight.

## Live demo (Hedera testnet)

```bash
pnpm --filter @eth/facilitator demo
```

| Step | Result |
|---|---|
| Unpaid request | `402 Payment Required` |
| Agent pays via mandate | `200` + trip plan + receipt — [HashScan](https://hashscan.io/testnet/transaction/0.0.11045937@1792525338.775588222) |
| Mandate after one call | 0.20 → 0.15 USDC remaining |
| Owner revokes, agent calls again | `402 simulation_reverted: MandateInactive` |
| Public spend log | HCS topic `0.0.11102632` gets `{"kind":"x402.settled", …}` |

## Config

| Env | Purpose |
|---|---|
| `HEDERA_*` | Operator account = fee payer |
| `SPEND_LOG_TOPIC_ID` | HCS topic for the public spend log (`pnpm --filter @eth/hedera create-topic`) |
| `PORT` | Facilitator port (default 8402) |
